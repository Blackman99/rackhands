rackhands documentation

rackhands is one static binary that is both a CLI and an MCP server for server BMCs. It speaks Redfish to Dell iDRAC, HPE iLO, Lenovo XCC, Supermicro and any DMTF-conformant BMC, and falls back to IPMI 2.0. It reads freely. It changes nothing unless you enable that class of operation and confirm the single machine it touches.

Install

$ go install github.com/Blackman99/rackhands/cmd/rackhands@latest

You can also download a release archive for linux, darwin or windows (amd64 or arm64) from GitHub Releases. Releases ship with checksums.txt. There is no runtime dependency: no Python, no ipmitool. IPMI is spoken natively.

For a one-off without a config file:

$ export RACKHANDS_PASSWORD='…'
$ rackhands --host https://10.20.0.11 --user root health
$ rackhands --ipmi 192.168.88.40 --user ADMIN sensors 192.168.88.40   # IPMI-only box

targets.yaml

rackhands reads $RACKHANDS_CONFIG, or ~/.config/rackhands/targets.yaml, or --config FILE. Keys under defaults apply to every target unless that target sets them itself.

defaults:
  username: rackhands-ro
  password_env: BMC_PASSWORD
targets:
  - name: db-01
    redfish: https://10.20.0.11     # https:// assumed if no scheme
    ipmi: 10.20.0.11                # optional; :623 assumed
    tags: [prod, db]
    allow: [power]                  # the per-target key for dangerous classes
  - name: lab-x10
    ipmi: 192.168.88.40             # IPMI only
    password_file: ~/.config/rackhands/lab.pass
audit_log: ~/.local/state/rackhands/audit.jsonl
KeyMeaning
nameUnique target name. You use it in commands and type it to confirm.
redfishBMC base URL. If you omit it, the target is IPMI-only.
ipmihost[:port] for IPMI 2.0 lanplus. With redfish set, this is the fallback.
ipmi_lan15Use IPMI 1.5 (lan) instead of lanplus, for very old BMCs.
username, password, password_env, password_fileCredentials. Prefer password_env or password_file. A read-only BMC account is enough for every read command.
insecureSkip TLS verification. The default is true because BMCs ship self-signed certificates. Prefer tls_fingerprint or ca_file with insecure: false.
tls_fingerprintSHA-256 of the BMC leaf certificate (hex, colon-hex, or sha256: prefix). Safer than insecure: true: the connection fails closed on mismatch. When set, the pin is the trust model for that target (it wins over insecure / ca_file). Print with rackhands tls-fingerprint TARGET.
ca_filePEM bundle used to verify the BMC certificate (proper PKI). Ignored for trust when tls_fingerprint is set.
session_authOpen one Redfish session per run (and delete it afterwards) instead of sending Basic auth on every request.
vendorForce a profile: dell, hpe, lenovo, supermicro or generic. It is normally auto-detected from the service root and manager.
allowDangerous classes this machine may receive: power, boot, bmc-reset, firmware, virtual-media or all.
tagsLets you select machines with tag:NAME in read commands.
timeoutPer-request timeout, e.g. 20s (the default). A whole command against one BMC gets three times this.
wait_timeoutHow long --wait follows a task before it stops watching, e.g. 45m. Default 30m. --wait-timeout overrides it for one run. The task itself keeps running on the BMC.

Read commands

A TARGET is a name, all (the default), or tag:NAME. Reads run against up to 8 BMCs at a time.

CommandWhat you get
rackhands targetsConfigured BMCs, addresses, tags and the dangerous classes each one effectively has enabled right now.
rackhands inventory [T…]Vendor, model, serial, BIOS and BMC firmware, CPU and memory summary, power state, and the effective privilege of the account rackhands logs in with (see read-only account).
rackhands health [T…]Overall OK / Warning / Critical plus every component that is not OK. It uses vendor rollups where they exist (iDRAC subsystem rollups, iLO AggregateHealthStatus), adds failed, worn or failure-predicted drives and degraded volumes (see storage health) and a one-line storage summary, and exits 1 if anything is unhealthy.

rackhands storage [T…] [--problems]RAID controllers (model, firmware), drives (media, size, health, media life left, location) and volumes (RAID level, size, member drives, state). --problems keeps only what is not OK. Exits 1 if a controller, drive or volume is not OK. Needs no --allow.

Each one prints a plan first: what will be sent, to which URL, with which body, and the current state. Then it asks you to type the target name. In scripts, pass --yes NAME (it must be the exact name of the target). --dry-run prints the plan and stops.

Firmware tasks

A BMC accepts a firmware update in seconds and spends the next minutes, sometimes half an hour, downloading, verifying and flashing it. --wait follows that work until it ends. Watching only reads, but it does not loosen the update: firmware-update … --wait still needs --allow firmware, the target's allow: and the confirmation. --dry-run shows the watch in the plan and sends nothing.

$ rackhands --allow firmware firmware-update db-01 https://repo/iDRAC.EXE --yes db-01 --wait
SENT  db-01: accepted (HTTP 202), task /redfish/v1/TaskService/Tasks/JID_001
      watching JID_001 until it ends (at most 30m; Ctrl-C stops watching, not the update)
WAIT  db-01 JID_001  Running      40% ████░░░░░░  Installing the iDRAC firmware package.  12s
DONE  db-01: JID_001 completed in 3m02s — Job completed successfully.
$ rackhands task db-01
db-01  via redfish
ID       KIND       STATE      %     NAME                              MESSAGE
JID_003  iDRAC job  Scheduled  0%    Firmware Update: BIOS             Task successfully scheduled.
JID_002  iDRAC job  Failed     0%    Firmware Update: PERC H755 Front  Unable to verify Update Package signature.
JID_001  iDRAC job  Completed  100%  Firmware Update: iDRAC            Job completed successfully.

On a terminal the WAIT line rewrites itself; in a log you get one line per change. rackhands polls every 2 seconds, backs off to 15 seconds while nothing changes, and honours Retry-After. A BMC that stops answering, or answers 503, while it restarts to apply its own firmware is polled until it comes back, and a lost Redfish session is opened again. Watching ends at wait_timeout.

HPE iLO 5SimpleUpdate returns no task, so rackhands reads Oem.Hpe.State and FlashProgressPercent on UpdateService as the pseudo task ilo-flash. A Complete left over from an earlier flash is ignored.
Lenovo XCCThe task monitor under TaskService/TaskMonitors, then its Task.

After a watched update, the audit log gets a task entry with the final state, percent, message, how long rackhands watched and how long the BMC took. Watching an existing task with rackhands task or get_task is a read and is not audited.

Storage health

A failed disk in a RAID5 set is the classic problem nobody sees until the second disk fails. health now reads the storage subsystem on every Redfish BMC and treats a failed drive or a degraded volume like a dead PSU: it is listed as a problem and makes the command exit 1. Each report ends with a storage line, so a healthy box shows that storage was actually checked.

$ rackhands health db-01

A drive the BMC still calls OK becomes a Warning when it reports FailurePredicted, or less than 10% PredictedMediaLifeLeftPercent; the NOTE column then says BMC says OK, so you can see why rackhands disagrees. Rebuilds show their progress (Rebuild 37%). Columns that are empty on every row are left out. Sizes are decimal (TB, GB), as on the drive label.

Where it comes fromWhen
DMTF StorageThe normal case: Systems/…/Storage with its Controllers collection or inline StorageControllers, Drives and Volumes. Subsystems with no drives and no volumes (iDRAC's chipset AHCI, CPU-attached NVMe roots) are skipped when healthy.
HPE SmartStorageiLO 4 and older iLO 5 firmware describe Smart Array controllers only in the OEM tree: ArrayControllers, DiskDrives, LogicalDrives. Capacities in MiB, SSD wear as SSDEnduranceUtilizationPercentage (used, so rackhands shows 100 minus it).
DMTF SimpleStorageOnly when nothing else is there. You get device health and size, but no volumes, wear or failure prediction, and a note says so.
NothingThe storage line says not exposed by this BMC. That does not fail health: rackhands reports what the BMC knows and does not guess.

Storage is read-only, like every other read: it needs no --allow, sends only GETs and is not audited. Over IPMI there is no storage data at all (no standard command lists controllers, drives or RAID sets), so rackhands storage on an IPMI-only target exits 2 with needs Redfish, and health notes that storage was not checked.

The safety model

  1. Off by default. Without --allow (or RACKHANDS_ALLOW), every dangerous command is refused with exit 3, and the MCP server does not list the tools at all.
  2. Two keys. The runtime --allow CLASS and the target's allow: list must both name the class. A mistyped target name or a box that nobody opened is refused. Ad-hoc --host targets have no config file, so for them only the runtime key applies.
  3. One machine. all, tag: and multiple names are refused for dangerous classes.
  4. Confirmation. On the CLI you type the name, or pass --yes NAME. With no terminal and no --yes, rackhands refuses. Over MCP the first call returns the plan and a token. The token is HMAC-signed, valid for 2 minutes and usable once. It is bound to the target, class, action, arguments and the protocol that will carry the request.
  5. Audit. Every refusal, plan, rejected token, execution and failure is appended to a JSONL file.

Defence in depth: a read-only BMC account

Give agents a read-only BMC account, and keep a separate, privileged config for humans. The gate above is enforced by rackhands. The strongest guarantee is enforced by the BMC: an account with the Redfish ReadOnly role (on iLO, an account without the Virtual Power and Reset, iLO Config, Virtual Media and Host BIOS privileges) or the IPMI User privilege cannot power anything off, whatever program holds the password. Every read command works with such an account.

rackhands inventory and the MCP get_inventory tool report the effective privilege of the account each target logs in with, under account: role, can_control, privileges and where it came from. Over Redfish rackhands finds its own user in AccountService/Accounts and reads RoleId and the role's privileges, or the iLO Oem.Hpe.Privileges flags. Over IPMI it uses Get Session Info and Get User Access, and a read-only IPMI account that is refused an Administrator session gets a User session instead. When a target has no dangerous allow: classes but its account could power it off, rackhands adds a warning (and prints WARN on stderr). This is detection only: rackhands never changes BMC accounts. When the BMC hides AccountService from the account, the role is Unknown.

$ rackhands --json inventory x11 | jq '.[0].data.account'
{"user": "ADMIN", "role": "Administrator", "can_control": true,
 "warning": "logs in as Administrator, which can power off or reconfigure this machine, but no dangerous class is allowed for it; use a read-only BMC account (Redfish ReadOnly role, IPMI User privilege)", …}

  "command": "rackhands",
  "args": ["mcp"],

Point the MCP server at a config whose BMC accounts are read-only (Redfish ReadOnly, IPMI User); get_inventory shows each account's effective role and warns about over-privileged ones (details).

get_health carries a storage section next to problems; get_storage returns the full lists, with source saying whether they came from Storage, SmartStorage or SimpleStorage.

Read tools are annotated readOnlyHint, and dangerous ones destructiveHint. A dangerous tool called without a token returns {"status": "confirmation_required", "plan": …, "confirm_token": …, "next": …}. Called again with the token, it returns {"status": "done", "result": …}. The server instructions tell the agent to show the plan and wait for a human yes. The token makes sure that what runs is exactly what was shown.

A confirmed update_firmware answers with a task_ref and a next hint for get_task. With wait_seconds it also watches the task and returns {"task": {"verdict", "task", "elapsed_s", …}}. wait_seconds is not part of the confirmed request, so it does not change the token. While a watch runs, the server sends MCP progress notifications (state, percent, message) when the client asked for them.

Vendor notes

VendorWhat rackhands does differently
Dell iDRAC 8/9Reads the hardware log from Sel, with the Lifecycle log only under --all-logs. Adds the DellSystem subsystem rollups to health. Hides Previous- and Available- firmware copies. Follows firmware updates through the iDRAC job (JobState), and reports a job scheduled for the next reboot as staged. Reads PERC storage under RAID.SL.* / RAID.Integrated.*, with DellPhysicalDisk / DellVolume RaidStatus (Failed, Degraded, Rebuilding).
HPE iLO 4/5/6Uses AggregateHealthStatus from Oem.Hpe (or Oem.Hp on iLO 4) for health. Maps IML Oem.Hpe.Severity (Caution becomes Warning). Fetches log entries that are not inlined. Sends Manager.Reset without a ResetType. Uses the OEM virtual media actions. Ignores thresholds reported as 0. Follows iLO 5 firmware flashes through Oem.Hpe.State on UpdateService. Falls back to the Smart Array SmartStorage OEM tree when there is no DMTF Storage (iLO 4).
Lenovo XCC/XCC2Reads PlatformLog. Uses the Sensors collection when there is no Thermal/Power. Sends an If-Match ETag on every PATCH; XCC rejects a PATCH without one. Follows firmware updates through the task monitor. Reads RAID adapters from the Storage Controllers collection.
Supermicro X11+Reads Log1 on the manager. On X11 boards whose virtual media is OEM-only, virtual media is reported as unsupported up front instead of failing halfway. Follows drive links into /Chassis, maps a volume that only has VolumeType to a RAID level, and shows rebuild progress from Operations.
Generic DMTFUses the standard schema only: Thermal/Power or Sensors, LogServices with LogEntryType SEL, SimpleUpdate, InsertMedia, TaskService, Storage (or SimpleStorage when that is all there is).

Units are normalised (Cel to C, Percent to %), severities map to OK / Warning / Critical, and event times are UTC.

IPMI and fallback

With both redfish and ipmi set, rackhands tries Redfish first. It falls back to IPMI when the service is unreachable, does not support the operation, or answers 404, 501 or 503. It does not fall back on 401 or 403: a wrong password should be fixed, not hidden by trying another protocol. Results say via: "ipmi (fallback)", and JSON adds fallback_reason.

Over IPMI you get FRU inventory, threshold sensors with health from the threshold status, SEL, chassis status faults, power state and control, boot device and BMC cold reset. Firmware update, virtual media and storage health are Redfish-only. Over IPMI, firmware shows only the BMC revision, and boot order is not available. SDR and SEL walks retry automatically when another client cancels the reservation.

Output and exit codes

--json prints a list of {"target", "via", "fallback_reason"?, "data"?, "error"?} for fleet reads, and {"target", "via", "data"} for single-target reads. One unreachable BMC does not hide the others: its entry carries an error.

CodeMeaning
0OK
1health or storage found something that is not OK
2An error occurred (including any BMC in a fleet read failing)
3Refused, unsupported, or not confirmed; nothing was sent
4A watched task did not complete: failed, cancelled, needs a human, vanished, or still running at the deadline
130You stopped watching with Ctrl-C (the task keeps running)

Audit log

The audit log is at ~/.local/state/rackhands/audit.jsonl by default. Override it with --audit-log FILE, RACKHANDS_AUDIT_LOG or audit_log:, or turn it off with --audit-log off. One JSON object per line:

{"time":"2026-10-12T08:14:03Z","actor":"mcp","phase":"planned","op":{"target":"db-01","class":"power","action":"force-off","args":{"via":"redfish"}},"summary":"power force-off db-01 …","method":"POST","path":"/redfish/v1/Systems/…/ComputerSystem.Reset","body":{"ResetType":"ForceOff"}}
{"time":"2026-10-12T08:14:31Z","actor":"mcp","phase":"executed","op":{…},"result":"accepted (HTTP 204)"}
{"time":"2026-10-19T02:13:04Z","actor":"cli","phase":"task","op":{"target":"db-01","class":"firmware","action":"update",…},"task":"/redfish/v1/TaskService/Tasks/JID_001","verdict":"completed","task_state":"Completed","percent_complete":100,"message":"Job completed successfully.","watched_s":184.2,"bmc_duration_s":182}

Phases: refused, planned, token-rejected, executed, failed, and task (the outcome of a watched firmware update).

How it is tested

Unit tests replay vendor mockups (Dell R750, HPE DL380 Gen10 on iLO 5 and DL360 Gen9 on iLO 4, Lenovo SR650 V2, Supermicro X11), each with its storage quirks and a failed, worn or degraded drive or volume except the healthy Lenovo, through an in-process Redfish server that records every write. Task resources in the mockups carry the states a running task goes through, so a firmware update can be followed from 0% to the end, including a BMC that drops off the network mid-flash. CI then runs the real binary (test/integration.sh) against the DMTF Redfish-Mockup-Server, which serves DMTF's public-rackmount1 mockup and the five vendor mockups, and against OpenIPMI ipmi_sim over a real RMCP+ session. The MCP server is exercised over stdio through the full plan, token and done sequence.

FAQ

Why not just give the agent ipmitool or curl? Because nothing stands between "check the fans" and chassis power off. rackhands gives the agent the reads and nothing else unless you open a class, and even then a human approves each request.

Can I use it without an agent? Yes. The CLI is a complete tool on its own.

Does it change BIOS settings, RAID, or BMC users? No. See GOAL.md.

My vendor behaves differently. Open an issue with an anonymised capture of the relevant Redfish resources. New quirks are added as mockups first.
